# تقرير الجدوى — GENESIS

التاريخ: 2026-11-26. يعتمد على [تقرير الاستكشاف](DISCOVERY_REPORT.md) و[مصفوفة القدرات](CAPABILITY_MATRIX.md) و[مراجعة السياسات](ANDROID_POLICY_REVIEW.md).

## 1. الخلاصة

**GENESIS ممكن كمنتج حقيقي على Google Play، لكن بشكل مختلف عن "وكيل يتحكم في الهاتف بالكامل".**

- ممكن: وكيل يفهم طلبك بالعربية أو الإنجليزية، يخطط، يجهّز المحتوى، يفتح التطبيقات والمحادثات الصحيحة بالمحتوى جاهزاً، يتابع الإشعارات بإذنك، يجدول التذكيرات والمهام، يحفظ المهام ويستأنفها، ويطلب موافقتك قبل أي إجراء حساس.
- القيد الأكبر: منذ 28 يناير 2026 تمنع Google Play استخدام خدمة إمكانية الوصول (AccessibilityService) لوكيل يخطط وينفّذ بنفسه داخل التطبيقات الأخرى. لذلك **الخطوة الأخيرة داخل WhatsApp أو Facebook (زر الإرسال أو النشر) يضغطها المستخدم**، إلا حيث توجد واجهة رسمية (مثل Pages API لصفحات Facebook، أو زر الرد في الإشعار بعد دراسته).
- هذا القيد ليس ضعفاً هندسياً يمكن تجاوزه؛ هو سياسة متجر. أي تصميم يتجاهله سيُرفض أو يُحذف من المتجر.

## 4. استراتيجية الذكاء الاصطناعي: الاستقلال عن قوة النموذج

### 4.1 المبدأ

النموذج **مستشار قابل للاستبدال**، والمحرّك المحلي هو المنتج. النموذج يقترح الخطة ويكتب النصوص فقط. كل ما هو حتمي (التحقق من الإجراءات، الصلاحيات، الخطورة، الموافقة، الجدولة، إعادة المحاولة، الإلغاء، التحقق من النتيجة، الاستعادة، حالة المهمة) ينفّذه كود محلي لا يعتمد على النموذج. هذا يخفض التكلفة والتأخير ويجعل النماذج الضعيفة مفيدة.

### 4.2 دعم المزوّدين الثلاثة (تم التحقق من الوثائق الرسمية)

| المزوّد | المخرجات المهيكلة (JSON وفق مخطط) | ملاحظات مهمة |
|---|---|---|
| **Claude** (Anthropic) | مدعومة عبر `output_config.format` بنوع `json_schema`، لجميع النماذج حسب الوثيقة | لا تتوافق مع الاقتباسات (citations) ولا مع التعبئة المسبقة للرد؛ قد يُرجع رفضاً (`refusal`) أو يُقطع عند حد الرموز؛ حدود لتعقيد المخطط. [المرجع](https://platform.claude.com/docs/en/build-with-claude/structured-outputs) |
| **OpenAI** | مدعومة: في Responses API عبر `text.format` بنوع `json_schema` مع `strict: true`، وفي Chat Completions عبر `response_format` | متاحة في النماذج الحديثة بدءاً من GPT-4o؛ النماذج الأقدم تستخدم "وضع JSON" الذي **لا يضمن** الالتزام بالمخطط. [المرجع](https://developers.openai.com/api/docs/guides/structured-outputs) |
| **Gemini** (Google) | مدعومة عبر `response_format` بنوع `application/json` مع `schema` | "يتجاهل النموذج الخصائص غير المدعومة"، وقد تُرفض المخططات الكبيرة جداً؛ دعم يختلف بين النماذج. [المرجع](https://ai.google.dev/gemini-api/docs/structured-output) |
| **متوافق مع OpenAI** (نماذج محلية أو مزوّدون آخرون) | غير مضمونة | نعاملها افتراضياً كنموذج ضعيف حتى يثبت التقييم العكس |

الخلاصة: حتى مع وجود المخرجات المهيكلة، **يجب** أن يتحقق GENESIS محلياً من كل خطة، لأن الرفض والقطع والمخططات غير المدعومة ممكنة لدى الجميع.

### 4.3 ثلاثة ملفات ذكاء

| الملف | أقصى خطوات للخطة | ميزانية السياق | الاستخدام |
|---|---|---|---|
| BASIC (أساسي) | 3 | ~4 آلاف رمز | أوامر قصيرة، قوالب جاهزة، قرار واحد في كل مرة |
| STANDARD (قياسي) | 10 | ~16 ألف رمز | خطط متعددة الخطوات وشرطية |
| ADVANCED (متقدم) | 25 | ~64 ألف رمز | مهام معقدة ومترابطة |

الاختيار **متحفظ**: نموذج غير مُقيَّم، أو حجم سياقه غير معروف، يُعامل كـ BASIC. لا يُحكم على النموذج من اسمه التسويقي. يمكن للمستخدم الاختيار يدوياً. الحدود الرقمية مبدئية وتُضبط بنتائج اختبارات التقييم.

### 4.4 سلسلة الرجوع للمخرجات (من الأقوى للأضعف)

1. المخرجات المهيكلة الأصلية حيث يدعمها النموذج.
2. استدعاء الأدوات (Tool Calling) حيث يدعمه.
3. طلب JSON بمخطط مختصر ومثال واحد.
4. تحليل صارم للـ JSON مع رفض أي حقل غير معروف.
5. التحقق من المخطط (الأنواع والحقول الإلزامية).
6. إصلاح محدود للصياغة فقط (استخراج JSON من نص محيط، إزالة الفواصل الزائدة، تصحيح علامات الاقتباس) دون تخمين أي محتوى.
7. تقسيم المهمة: طلب الخطوة التالية فقط.
8. قوالب محلية جاهزة للطلبات الشائعة (فتح تطبيق، تذكير، مسودة رسالة) تُطابق دون نموذج.
9. سؤال المستخدم سؤالاً محدداً.

**قاعدة:** لا تُنفَّذ أي خطة مشوهة، ولا يتحول نص حر من النموذج إلى أوامر جهاز أبداً.

### 4.5 النماذج التي لا تدعم Tool Calling أو سياقها محدود

- لا يعتمد التصميم على Tool Calling؛ الخطط تُطلب كـ JSON وتُحلل محلياً.
- السياق المحدود: ضغط السياق، ذاكرة خاصة بكل مهمة، استرجاع الأجزاء ذات الصلة فقط، تاريخ محادثة محدود، ميزانية رموز لكل طلب، وعدم إرسال المحادثات أو الإشعارات كاملة.
- عند فشل نموذج ضعيف: حفظ المهمة → تبسيطها → طلب القرار التالي فقط → قواعد محلية → سؤال المستخدم. يمكن التبديل لنموذج آخر دون فقدان حالة المهمة لأنها محفوظة في المحرّك.

### 4.6 تقييم النماذج (مخطط لاحقاً)

مجموعة مهام ثابتة بالعربية والإنجليزية والمختلطة، تُشغَّل على نماذج قوية ومتوسطة وضعيفة، وتقيس: نسبة الخطط الصالحة، إتمام المهمة، الالتزام بالمخطط، رفض الإجراءات الخطرة، الرموز المستهلكة، التأخير، نسبة الاستعادة، والطلبات غير الضرورية. **لا توجد نتائج تقييم بعد**؛ تحتاج مفاتيح API منك عند الوصول لتلك المرحلة.
