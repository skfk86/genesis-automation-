## 1. المبادئ الحاكمة

1. **المحرّك هو المنتج، والنموذج مستشار قابل للاستبدال.** النموذج يقترح ويكتب؛ المحرّك المحلي يقرر وينفذ ويتحقق.
2. **لا شيء يُنفَّذ خارج الكتالوج.** كل إجراء مُعرَّف مسبقاً بمعاملات مُنمَّطة، وخطورة، وطريقة تحقق.
3. **أقوى أتمتة ممكنة على Android.** المحرّك يختار تلقائياً أقوى وسيلة متاحة لكل خطوة: واجهة رسمية ← رد عبر الإشعار ← **التحكم بالواجهة كالإنسان** ← موافقة بضغطة ← تجهيز يكمله المستخدم. الحدود الوحيدة: قيود نظام Android، وصلاحيات المستخدم، وشروط التطبيقات الأخرى (التي نوضح مخاطرها ولا نخفيها).
4. **الأدلة قبل النجاح.** "محاولة" ≠ "مقبول" ≠ "مكتمل" ≠ "متحقق منه".
5. **محلي أولاً.** كل البيانات على الجهاز؛ الشبكة فقط لمزوّد الذكاء الاصطناعي والخدمات التي ربطها المستخدم.
6. **المستخدم يتحكم.** أذونات محدودة النطاق والمدة، زر إيقاف طارئ، سجل كامل، ولا أتمتة خفية.
7. **نواة Kotlin خالصة.** منطق المحرّك لا يعتمد على Android، فيُختبر بسرعة ولا يلمس الجهاز بالخطأ.

## 2. الطبقات

```
┌──────────────────────────────────────────────────────────────┐
│ الواجهة (features/*)   Compose + ViewModel، حالة غير قابلة للتغيير │
├──────────────────────────────────────────────────────────────┤
│ التنسيق (orchestration) MissionCoordinator، AgentPipeline         │
├───────────────┬───────────────┬──────────────┬───────────────┤
│ الوكيل agent  │ المهام mission │ الذاكرة memory │ السياسات policy │  ← Kotlin خالص
├───────────────┴───────────────┴──────────────┴───────────────┤
│ محرّك الأتمتة automation: الكتالوج، المنفّذ، التحكم بالواجهة، التحقق │  ← Kotlin خالص
├──────────────────────────────────────────────────────────────┤
│ المحوّلات adapters: UI (Accessibility/Shizuku)، Notification، Intent، API │  ← Android
│ بوابة الذكاء الاصطناعي ai-gateway: Claude، OpenAI، Gemini، متوافق   │  ← HTTP
│ البيانات data: Room، DataStore، خزنة المفاتيح (Keystore)            │  ← Android
└──────────────────────────────────────────────────────────────┘
```

**قاعدة الاعتماد:** الطبقات العليا تعتمد على واجهات (interfaces) الطبقات الدنيا فقط. وحدات `domain/*` و`automation/*` الأساسية لا تعتمد على Android. المحوّلات وطبقة البيانات تنفّذ واجهات معرّفة في النواة (مبدأ عكس الاعتماد).

## 4. محرّك الأتمتة

### 4.1 القدرات والمحوّلات (يُعاد بناؤه عن المسودة)

بدلاً من قائمة قدرات ثابتة، **كل محوّل يعلن قدراته** حسب حالة الجهاز الفعلية:

```kotlin
interface CapabilityProvider {
    val id: AdapterId
    suspend fun discover(): List<CapabilityOffer>   // ماذا أستطيع الآن؟
}

data class CapabilityOffer(
    val capability: CapabilityId,        // مثل "message.reply"
    val target: TargetSelector,          // مثل التطبيق com.whatsapp أو حساب Gmail
    val automationLevel: AutomationLevel,// FULL / ONE_TAP / HANDOFF
    val requirements: List<Requirement>, // صلاحيات/حسابات ناقصة إن وُجدت
    val verification: VerificationMethod,
    val mode: OperatingMode,             // أقل وضع تشغيل يحتاجه (0–4)
    val accountRisk: AccountRisk,        // NONE / LOW / TOS_RISK (مثل الأتمتة داخل واتساب)
)
```

مثال: قدرة "الرد على رسالة" للهدف WhatsApp قد تُعرض من عدة محوّلات:

| المحوّل | مستوى الأتمتة | الشرط |
|---|---|---|
| `notifications` (زر الرد في الإشعار) | FULL | إذن مستمع الإشعارات + وجود إشعار حديث بزر رد |
| `intents` (wa.me مع نص) | HANDOFF | WhatsApp مثبت |
| `ui-accessibility` (فتح المحادثة، كتابة، إرسال، التحقق من الفقاعة) | FULL + تحقق قوي من الشاشة | الوضع 2 + شاشة مفتوحة + إقرار المستخدم بمخاطر شروط واتساب |
| `ui-shizuku` | FULL | الوضع 3 + شاشة مفتوحة |

### 4.2 اختيار الوسيلة (Strategy Resolver)

لكل خطوة يختار المحرّك **أعلى مستوى أتمتة متاح ومسموح**:

```
واجهة رسمية (FULL، تحقق قوي)
  ← رد/إجراء عبر الإشعار (FULL، تحقق متوسط، يعمل والهاتف مقفل)
    ← التحكم بالواجهة عبر Accessibility أو Shizuku (FULL، تحقق من الشاشة، يحتاج شاشة مفتوحة)
      ← موافقة بضغطة من الإشعار ثم تنفيذ FULL
      ← تجهيز يكمله المستخدم (HANDOFF، تأكيد المستخدم)
        ← تعذّر: شرح السبب واقتراح ما ينقص (صلاحية/ربط حساب)
```

السياسة (القسم 8) قد تخفض المستوى: مثلاً FULL متاح تقنياً لكن لا يوجد إذن مسبق، فيصبح "موافقة بضغطة".

### 4.3 تعريف الإجراء

يُحتفظ بتعريف المسودة ويُوسّع:

| الحقل | المعنى |
|---|---|
| `id`، `params` | معرّف ثابت ومعاملات مُنمَّطة (نص بطول أقصى، https فقط، E.164، معرّف محادثة...) |
| `capability` | القدرة المطلوبة (تُطابق مع عروض المحوّلات) |
| `risk` | LOW / MEDIUM / HIGH / CRITICAL |
| `sideEffect` | هل يغيّر شيئاً خارج الجهاز؟ |
| `idempotency` | آمن التكرار أم لا (الإرسال والنشر: لا) |
| `timeout`، `retry` | المهلة وسياسة إعادة المحاولة (ممنوعة لغير آمن التكرار) |
| `expectedOutcome`، `verification` | النتيجة المتوقعة وطريقة التحقق |
| `cancellation` | قابل للإلغاء، أو غير قابل بعد التسليم |

**الكتالوج المبدئي للإصدار الأول** (يُنفّذ تدريجياً):
`app.launch`، `web.open`، `share.text`، `message.draft` (رابط بنص)، `message.reply` (عبر الإشعار)، `notification.action`، `email.draft`، `email.send` (Gmail API)، `email.search_summarize` (Gmail API)، `calendar.insert`، `calendar.query`، `reminder.create`، `files.organize`، `ai.generate_text`، `ai.summarize`، `facebook.page_post` (Pages API)، `post.prepare_handoff`، `telegram.business_reply`، `user.ask` (سؤال/موافقة).

### 4.4 دورة تنفيذ الإجراء

```
Validated → Resolve strategy → Check policy → [Approval?]
  → Outbox: write "Attempted" + idempotency key   ← يُحفظ قبل التنفيذ
  → Adapter.execute (timeout, cancellable)
  → record Accepted / Completed / Failed / Declined
  → Verifier → Verified (مع الدليل) أو يبقى Completed
  → next step / recovery
```

**صندوق الإرسال (Outbox):** كل إجراء له أثر خارجي يُسجَّل قبل التنفيذ مع مفتاح فريد. بعد تعطل التطبيق يرى المحرّك "محاولة بلا نتيجة" فلا يكرر الإرسال، بل يتحقق (مثلاً عبر الواجهة الرسمية) أو يسألك.

### 4.5 التحقق

| الطريقة | مثال | قوة الدليل |
|---|---|---|
| استجابة واجهة رسمية | Pages API تعيد رقم المنشور؛ Gmail يعيد رقم الرسالة | قوي |
| قراءة بعد الكتابة | قراءة حدث التقويم بعد إضافته | قوي |
| تغيّر الإشعار | إشعار المحادثة يُحدَّث بعد الرد | متوسط (يحتاج تحقق على جهاز) |
| تأكيد النظام | WorkManager قبل المهمة | متوسط |
| تأكيد المستخدم | "هل أرسلت المنشور؟" | ضعيف، ويُعرض كذلك |

### 4.6 الاستعادة

- فشل مؤقت (شبكة، حد معدّل) لإجراء آمن التكرار: إعادة محدودة مع تأخير متزايد.
- فشل لإجراء غير آمن التكرار: لا إعادة تلقائية؛ تحقق أولاً ثم اسأل.
- تعذّر الوسيلة: جرّب الوسيلة التالية في سلّم الاختيار (مثلاً من FULL إلى ONE_TAP).
- حالة غير مؤكدة: المهمة تنتقل إلى "بانتظار المستخدم" مع سؤال محدد.

## 5. نظام المهام

### 5.1 أنواع المهام

| النوع | مثال | السلوك |
|---|---|---|
| **فورية** | "ذكّرني بالاجتماع غداً" | خطة → تنفيذ → تقرير |
| **مراقِبة (Standing)** | "تابع محادثتي مع أحمد حتى أعود" | تبقى نشطة؛ تستيقظ عند حدث (إشعار من أحمد)؛ تنفذ دورة قصيرة؛ تنتهي بانتهاء المدة أو بأمرك |
| **مجدولة** | "كل صباح لخّص بريدي" | محفّز زمني عبر WorkManager |
| **أتمتة** (منشئ الأتمتة) | "إذا وصلت رسالة فيها كلمة فاتورة، احفظها في مجلد" | محفّز + شروط + إجراءات، بلا نموذج إن أمكن |

### 5.2 آلة الحالات

يُحتفظ بها من المسودة (11 حالة، جدول انتقالات صريح، الحالات النهائية لا تخرج):

```
Draft → Planning → (AwaitingApproval ⇄ Planning) → Ready → Running
Running ⇄ Paused (عبر Ready) · Running → WaitingForUser · Running → Recovering
أي حالة غير نهائية → Cancelled · Running → Completed | Failed
```

تُضاف للمهام المراقِبة حالة فرعية داخل `Running`: **Idle (بانتظار حدث)** و**Handling (تعالج حدثاً)**، حتى لا تبدو "تعمل" وهي نائمة.

### 5.3 التخزين (Room)

| الجدول | المحتوى |
|---|---|
| `missions` | المعرّف، الطلب الأصلي، النوع، الحالة، نسخة الخطة، التواريخ، التقرير النهائي |
| `mission_steps` | الخطوة، الإجراء، المعاملات، الاعتماديات، الوسيلة المختارة، النتيجة |
| `state_changes` | كل انتقال حالة مع السبب والوقت |
| `outbox` | الإجراءات ذات الأثر الخارجي: مفتاح فريد، حالة، دليل |
| `approvals` | كل موافقة: من، متى، على ماذا بالضبط |
| `standing_rules` | الأذونات المسبقة (القسم 8.3) |
| `memory_items` | الذاكرة (القسم 6) |
| `audit_log` | سجل غير قابل للتعديل (إضافة فقط)، بعد الإخفاء |
| `automations`, `automation_runs` | منشئ الأتمتة وسجله |

كل تغيير في المخطط يرافقه ترحيل واختبار ترحيل.

### 5.4 التشغيل في الخلفية

| الحاجة | الآلية |
|---|---|
| تنفيذ مؤجل أو دوري | WorkManager (توقيت تقريبي) |
| الاستيقاظ عند رسالة | مستمع الإشعارات يوقظ المهمة المراقِبة |
| مهمة طويلة مرئية | خدمة أمامية بأضيق نوع مع إشعار دائم، فقط عند الحاجة |
| فتح تطبيق والـ GENESIS في الخلفية | إشعار يضغطه المستخدم (قيد Android) |
| بعد إعادة تشغيل الجهاز | WorkManager يعيد الجدولة؛ المهام المراقِبة تُستأنف؛ ما كان "قيد المحاولة" يمر على الاستعادة |

| سياق المحادثة | آخر الرسائل مع GENESIS | Room | محدود العدد، يُلخَّص | الأجزاء الحديثة فقط |
| سياق المهمة | ما حدث في مهمة أحمد | Room | حتى انتهاء المهمة + مدة يحددها المستخدم | الملخص فقط |
| تفضيلات المستخدم | "ردودي رسمية"، "لا تحدد مواعيد" | Room | دائم حتى يحذفه المستخدم | نعم عند الصلة |
| قواعد الأتمتة | القواعد التلقائية | Room | دائم | **لا**؛ تُطبّق محلياً |
| سجل التنفيذ | ما نُفّذ ومتى | Room | قابل للضبط (افتراضياً 90 يوماً) | لا |
| الذاكرة المؤقتة | محتوى إشعار قيد المعالجة | الذاكرة فقط | تنتهي بانتهاء المعالجة | المقتطف اللازم فقط |

**قواعد:**
- كل عنصر ذاكرة يحمل **مصدره ودرجة ثقته**: من المستخدم (موثوق) أو من محتوى خارجي (غير موثوق). المحتوى الخارجي لا يتحول إلى تعليمات أو تفضيلات أبداً.
- الاسترجاع حسب الصلة بالمهمة وضمن ميزانية الرموز، وليس إرسال كل شيء.
- المستخدم يرى كل الذاكرة ويحذف أي عنصر أو كل شيء.
- لا يُحفظ محتوى حساس (رموز OTP، كلمات مرور) أبداً؛ يُكتشف ويُخفى قبل التخزين.

## 7. بوابة مزوّدي الذكاء الاصطناعي

### 7.1 الواجهة

```kotlin
interface AIProvider {
    val kind: ProviderKind                 // ANTHROPIC, OPENAI, GEMINI, OPENAI_COMPATIBLE
    suspend fun listModels(): ProviderResult<List<ModelInfo>>
    suspend fun complete(request: ModelRequest): ProviderResult<ModelResponse>
    suspend fun testConnection(model: String): ProviderResult<Unit>
}
```

- `ModelRequest`: النموذج، تعليمات النظام، الرسائل، حد الرموز، **صيغة الإخراج** (نص حر أو JSON بمخطط)، الحرارة.
- `ModelResponse`: النص، الاستهلاك (إن أعلنه المزوّد)، سبب التوقف (انتهى/حد الرموز/رفض).
- `ProviderError`: مفتاح غير صالح، حد معدّل، رصيد منتهٍ، نموذج غير موجود، سياق كبير، انقطاع، شبكة، غير متوقع. لكل خطأ رسالة عربية واضحة وتصنيف "مؤقت أم يحتاج المستخدم".

### 7.2 المحوّلات (تم التحقق من الوثائق)

| المحوّل | المخرجات المهيكلة | ملاحظة |
|---|---|---|
| `ai:anthropic` | `output_config.format` بنوع `json_schema` | الرفض وحد الرموز ممكنان |
| `ai:openai` | Responses API: `text.format` بنوع `json_schema` و`strict: true` | النماذج الأقدم: وضع JSON بلا ضمان |
| `ai:gemini` | `response_format` بـ `application/json` و`schema` | يتجاهل الخصائص غير المدعومة |
| `ai:openai-compatible` | غير مضمونة | يُعامل كضعيف حتى يُقيَّم |

### 7.3 خط معالجة الطلب

```
النية/الخطوة
 → اختيار المزوّد والنموذج (حسب إعداد المستخدم والملف)
 → ميزانية الرموز (حسب الملف)
 → استرجاع الذاكرة ذات الصلة
 → إخفاء المحتوى الحساس
 → تجميع الطلب (تعليمات موثوقة + محتوى غير موثوق معزول بحدود عشوائية)
 → الاستدعاء (مهلة + إلغاء)
 → تحليل المخرجات (سلّم الرجوع، القسم 8.2 في تقرير الجدوى)
 → التحقق من الخطة محلياً
 → تسجيل الاستهلاك والتكلفة التقديرية
```

### 7.4 المفاتيح والتكلفة

- المفاتيح في خزنة مشفرة بـ Android Keystore، لا تظهر في السجلات، ولا تُرسل إلا للمزوّد صاحبها.
- عرض الاستهلاك كما يعلنه المزوّد فقط؛ **لا أسعار مخترعة**. إن عرف المستخدم السعر يمكنه إدخاله.
- حد أقصى للطلبات والرموز لكل مهمة ولكل يوم؛ لا تبديل صامت لمزوّد آخر.
- النموذج الاحتياطي يُستخدم فقط إن فعّله المستخدم صراحة.

## 8. استراتيجية النماذج الضعيفة

### 8.1 الموجّه المحلي أولاً (Local Intent Router)

قبل استدعاء أي نموذج، يحاول المحرّك مطابقة الطلب **محلياً** بقوالب عربية وإنجليزية للطلبات الشائعة:

| الطلب | المطابقة المحلية | يحتاج نموذجاً؟ |
|---|---|---|
| "افتح واتساب" / "open WhatsApp" | `app.launch(com.whatsapp)` | لا |
| "ذكّرني الساعة 5 بالدواء" | `reminder.create` | لا (تحليل الوقت محلياً) |
| "اكتب لأحمد إني متأخر" | `message.draft` + توليد نص قصير | نعم، لكتابة النص فقط |
| "تابع محادثتي مع أحمد حتى أعود" | قالب مهمة مراقِبة | نعم، لصياغة كل رد فقط |

هذا يخفض التكلفة، ويجعل GENESIS مفيداً حتى بلا نموذج للأوامر البسيطة.

### 8.2 الملفات الثلاثة

| | BASIC | STANDARD | ADVANCED |
|---|---|---|---|
| أقصى خطوات | 3 | 10 | 25 |
| السياق | ~4 آلاف رمز | ~16 ألفاً | ~64 ألفاً |
| أسلوب التخطيط | قالب + سؤال واحد في كل مرة | خطة كاملة | خطة كاملة مع اعتماديات |
| المهام المراقِبة | النموذج يكتب الرد فقط؛ القرار محلي | النموذج يقرر هل يرد | النموذج يدير الحوار ضمن القواعد |

الاختيار متحفظ (مجهول = BASIC)، والعتبات تُضبط من نتائج التقييم.

### 8.3 تقسيم المهمة عند الفشل

```
فشل التحليل → إصلاح صياغي محدود → إعادة الطلب بمخطط أبسط
  → طلب الخطوة التالية فقط → قالب محلي → سؤال محدد للمستخدم
```

حالة المهمة محفوظة في المحرّك، فيمكن تبديل النموذج في المنتصف دون فقدان شيء.

## 9. الصلاحيات والأمان

### 9.1 نموذج الصلاحيات الثلاثي

| النوع | أمثلة | كيف تُمنح | كيف تُفحص |
|---|---|---|---|
| صلاحيات Android وقت التشغيل | الإشعارات، الميكروفون، التقويم | نافذة النظام | `checkSelfPermission` قبل كل تنفيذ |
| وصول خاص من الإعدادات | مستمع الإشعارات، إمكانية الوصول، العرض فوق التطبيقات، تثبيت التحديثات، Shizuku | الإعدادات بعد شاشة إفصاح | فحص دوري، وإلغاؤه يوقف المهام المعتمدة عليه فوراً |
| صلاحيات الخدمات (OAuth) | Gmail، صفحات Facebook، بوت Telegram | تسجيل دخول الخدمة | رمز صالح + النطاقات المطلوبة |

مركز الصلاحيات يعرض لكل صلاحية: لماذا نحتاجها، أي ميزات تعتمد عليها، وزر سحبها.

### 9.2 قرار الموافقة (حتمي)

| الخطورة | الافتراضي |
|---|---|
| LOW | تلقائي |
| MEDIUM | موافقة، إلا بقاعدة مسبقة مطابقة |
| HIGH | موافقة، إلا بقاعدة مسبقة مطابقة **ومحددة بمحادثة/وجهة ومدة** |
| CRITICAL | ممنوع دائماً |
| الإيقاف الطارئ | كل شيء ممنوع |

### 9.3 القواعد التلقائية (الأذونات المسبقة) — يُعاد بناؤه

```
StandingRule(
  action = message.reply,
  target = محادثة أحمد في WhatsApp,
  validUntil = اليوم 18:00,
  maxExecutions = 20,
  contentConstraints = [لا مبالغ مالية، لا مواعيد، لا روابط],
  requireSignature = اختياري ("— مساعد علوش"),
)
```

- قبل كل تنفيذ تلقائي: تُفحص القيود **محلياً** على النص النهائي؛ أي خرق يحوّل الخطوة إلى موافقة بضغطة.
- لا تمتد القاعدة لمحادثة أخرى أو إجراء آخر.
- كل تنفيذ تلقائي يظهر في السجل وإشعار ملخص.

### 9.4 طبقات الحماية من حقن التعليمات

1. الفصل: تعليمات المستخدم موثوقة؛ الرسائل والإشعارات والصفحات والملفات بيانات غير موثوقة، معزولة بحدود عشوائية.
2. لا مفاتيح ولا بيانات غير لازمة في الطلب.
3. الكتالوج المغلق والتحقق الحتمي من الخطة.
4. القاعدة التلقائية لا يمكن إنشاؤها أو توسيعها بنص خارجي؛ فقط من واجهة المستخدم.
5. اختبارات حقن مخصصة (رسائل خبيثة بالعربية والإنجليزية) في مجموعة التقييم.

### 9.5 بقية الأمان

خزنة مفاتيح (Keystore)، HTTPS فقط، تعطيل النسخ الاحتياطي، إخفاء في السجلات، لا تقارير أعطال خارجية في الإصدار الأول، مكوّنات غير مكشوفة، سجل تدقيق بالإضافة فقط. التفاصيل في [نموذج التهديدات](../SECURITY_THREAT_MODEL.md).

## 10. تصميم التكاملات الخارجية

### 10.1 الواجهة المشتركة

```kotlin
interface Integration {
    val id: IntegrationId                    // whatsapp, telegram, facebook, gmail...
    val requiredAccounts: List<AccountSpec>  // مثل حساب Google أو صفحة Facebook
    fun actions(): List<ActionDefinition>
    suspend fun health(): IntegrationHealth  // مثبت؟ مربوط؟ صلاحيات ناقصة؟
}
```

### 10.2 كل تكامل

| التكامل | الوسائل حسب مستوى الأتمتة | ملاحظات |
|---|---|---|
| **المراسلة عبر الإشعارات** (مشترك لـ WhatsApp وTelegram وMessenger وSMS) | FULL: الرد عبر زر الإشعار · ONE_TAP: إشعار موافقة | الأساس لحالة "تابع محادثتي" |
| **WhatsApp** | FULL عبر الإشعارات · HANDOFF: `wa.me` بنص · Business API للتجاريين فقط | لا قراءة لسجل المحادثة |
| **Telegram** | FULL: بوت أعمال متصل (رسمي) أو الإشعارات · HANDOFF: `t.me/<user>?text=` | البوت يعمل حين يعمل GENESIS، أو بخادم إن قررت لاحقاً |
| **Facebook** | FULL: Pages API للصفحات · HANDOFF: تجهيز ونسخ وفتح التطبيق للحساب الشخصي | لا تعبئة مسبقة، لا تبديل حسابات |
| **Gmail** | FULL: Gmail API (إرسال، بحث، تلخيص) · HANDOFF: `mailto:` · قراءة الجديد من الإشعارات | يحتاج قرار تحقق Google |
| **التقويم** | FULL: `CalendarContract` مع تحقق بالقراءة · HANDOFF: شاشة الإضافة | |
| **الملفات** | FULL: داخل مجلد منحه المستخدم | |
| **المتصفح** | فتح روابط وCustom Tabs؛ جلب صفحات كمحتوى غير موثوق | لا تحكم في Chrome |

كل تكامل يحمل علامة `PLAY` أو `EXTENDED_ONLY` لكل وسيلة، فيُعرض للمستخدم بوضوح ما يتاح في نسخته.

## 11. معمارية الواجهة

- MVVM مع تدفق بيانات أحادي الاتجاه: الشاشة ← حدث ← ViewModel ← حالة جديدة غير قابلة للتغيير.
- كل شاشة لها حالات: تحميل، فارغ، خطأ، نجاح، وبيانات حقيقية فقط (لا تقدم وهمي).
- شاشة المهمة تعرض: ماذا يفعل الوكيل ولماذا، ما اكتمل، ما بقي، ما ينتظر موافقتك، الأخطاء، ومستوى التحقق لكل خطوة.
- نظام التصميم الداكن من المسودة (الألوان ونسب التباين المحسوبة) مع خطوط Inter وNoto Sans Arabic مضمّنة، ودعم RTL كامل.
